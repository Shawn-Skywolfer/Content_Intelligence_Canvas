# v0.3.28：模型接收停滞修复

## 证据与版本差异

v0.3.25 使用普通模型请求，v0.3.26 开始使用流式接收和实时日志。用户的新日志中，首轮 Wiki 检索规划正常完成，第二轮关系规划在 HTTP 200、1726 个推理字符、2 个正文字符后停止更新。不能据此认定触发网络风控，也尚未在用户环境复现唯一根因。

## 修复

- 网络接收与日志写入使用独立线程；诊断写入不再阻挡模型正文读取。
- 任务监督线程不依赖关闭 HTTP/TLS 连接来解除阻塞。连续无正文和推理内容超过配置超时（最多 60 秒）即结束等待，单次调用总时限 30 分钟。
- 收到完整结果后，即使 TLS 清理阻塞，也能交回完整响应。
- 关系规划超时后保留首轮已成功完成的大模型检索计划，继续查阅原始 Wiki；不会使用不完整 JSON 或模板冒充模型输出。
- 关系规划成功后的查询优先参与检索，避免被初轮查询的前五条截断。
- 无新内容心跳包含空闲时长；超时错误记录接收和日志线程的代码位置，不记录局部变量、API Key 或额外文档内容。
- 保留上版输入节点的正向、负向 Prompt 历史。

## 验证与限制

回归测试覆盖：正文出现后读取永久阻塞且 close 不唤醒、日志持久化阻塞、完成后 TLS 清理阻塞、关系规划超时继续检索，以及已有取消、部分输出、异常数据、结束标记和完整后端测试。Windows Release 工作流另行运行前端测试和启动检查。

这些是受控故障测试；不能替代用户代理、真实供应商和真实 Wiki 上的复测。监督可隔离阻塞读取，但操作系统不返回时后台守护线程可能持续到应用退出。不会无限重试或把不完整内容当作最终结果。
